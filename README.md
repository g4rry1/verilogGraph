# VerilogGraph

Интерактивный граф видов токенов SystemVerilog на Kotlin/Swing. В левой панели — все 352 `TokenKind` из закреплённой ревизии [slang](https://github.com/MikePopoloski/slang). В центре — вершина и непосредственные допустимые продолжения; щелчок по вершине продвигает просмотр. Сценарий `module` использует контекст `source_text`: после `endmodule` можно перейти к следующему объявлению. Для каждого продолжения показано, какие именованные правила Annex A могут начаться на этом токене. Кнопка `↺ файл` открывает начало исходного текста.

## Источники

- [IEEE Std 1800-2023](https://ieeexplore.ieee.org/document/10458102), Annex A — формальный синтаксис. [Страница IEEE](https://standards.ieee.org/ieee/1800/7743/) подтверждает редакцию и бесплатный доступ через IEEE Get. Из [публичной копии PDF](https://www.iccircle.com/static/upload/img20240319175450.pdf) извлечены правила вместе с цветовым выделением буквальных терминалов.
- [`scripts/grammar.txt`](https://github.com/MikePopoloski/slang/blob/dcc7ee97fb14f9be003de71e100d0c9601a993c9/scripts/grammar.txt) в slang — дополнительная текстовая транскрипция Annex A для сравнения.
- [`scripts/tokenkinds.txt`](https://github.com/MikePopoloski/slang/blob/dcc7ee97fb14f9be003de71e100d0c9601a993c9/scripts/tokenkinds.txt), [`LexerFacts.cpp`](https://github.com/MikePopoloski/slang/blob/dcc7ee97fb14f9be003de71e100d0c9601a993c9/source/parsing/LexerFacts.cpp) и [`Lexer.cpp`](https://github.com/MikePopoloski/slang/blob/dcc7ee97fb14f9be003de71e100d0c9601a993c9/source/parsing/Lexer.cpp) — виды токенов, фиксированные написания и разбиение составных лексем.
- [`NumberParser.h`](https://github.com/MikePopoloski/slang/blob/dcc7ee97fb14f9be003de71e100d0c9601a993c9/include/slang/parsing/NumberParser.h), [`NumberParser.cpp`](https://github.com/MikePopoloski/slang/blob/dcc7ee97fb14f9be003de71e100d0c9601a993c9/source/parsing/NumberParser.cpp) и [`SyntaxFacts.cpp`](https://github.com/MikePopoloski/slang/blob/dcc7ee97fb14f9be003de71e100d0c9601a993c9/source/syntax/SyntaxFacts.cpp) — сборка значения литерала из соседних токенов slang.

Конкретная ревизия slang и SHA-256 PDF указаны в [`SOURCE.txt`](src/main/resources/SOURCE.txt). Извлечённые данные включены в `src/main/resources`; PDF стандарта в репозитории нет. Импорт повторяется командами `python3 tools/import_slang.py /path/to/slang` и `python3 tools/extract_ieee_pdf.py /path/to/ieee1800-2023.pdf` (для второй требуется `pdftohtml`).

## Запуск

Требуются JDK 17+ и доступ к Maven Central для первого получения плагина Kotlin.

```bash
./gradlew run
./gradlew run --args='--cli'
./gradlew run --args='--cli source_text'
./gradlew run --args='--cli generate_region'
./gradlew check
./gradlew run --args='--check'
./gradlew run --args='--audit'
./gradlew run --args='--export-dot graph.dot'
./gradlew run --args='--preview preview.png'
./gradlew installDist
build/install/veriloggraph/bin/veriloggraph
build/install/veriloggraph/bin/veriloggraph --cli
```

`--cli` запускает интерактивный просмотр грамматики в терминале. `next` показывает допустимые следующие `TokenKind` и правила, которые могут начаться на каждом из них; `next endmodule` фильтрует список, `next *` показывает его полностью. `step module` или `step ModuleKeyword` добавляет токен к префиксу, `back` отменяет шаг, `use source_text` переключает на просмотр целого файла, `use package_declaration` выбирает отдельное правило. `rules [поиск]` и `tokens [поиск]` находят правила и токены; `rule <имя>` показывает текст правила; `global <токен> [поиск]` и `edge <от> <к>` показывают глобальные рёбра и их происхождение. Без фильтра длинный список ограничен первыми 40 строками. `help` выводит все команды, `quit` завершает сеанс. При запуске с аргументом `--cli <правило>` указанное правило выбирается сразу. Внутри CLI цепочка `step` проверяется в одном контексте; команда `global` показывает объединение рёбер без изменения текущего префикса и без меток начала правил.

`./gradlew check` запускает проверки графа автоматически. `--check` проверяет путь `module → Identifier → ; → endmodule`, вариант с `automatic`, буквальные скобки, числовую основу и системные проверки времени. `--audit` печатает обозначения, которые нельзя однозначно сопоставить с токеном. DOT экспортирует весь полученный граф с правилом происхождения на каждом ребре.
`--preview` сохраняет изображение сценария `module → …` без запуска оконной системы.

`./gradlew test` запускает 952 теста. Из них 200 — конкретные примеры и проверки ошибок для каталога, импорта, CLI, чисел, графа, DOT, PNG и разных конструкций SystemVerilog, включая границы после обычного и вложенного `endmodule`. Ещё по одному тесту создано для каждого из 750 имён правил Annex A: для 725 развёрнутых правил строится кратчайшая цепочка `TokenKind` и проверяется её прохождение; 17 правил сверяются с одним видом токена slang; 8 посимвольных правил отмечены отдельно, поскольку не образуют самостоятельной цепочки токенов. Два теста проверяют границы этого покрытия. Автоматически построенные пути проверяют согласованность импортёра и пошагового просмотрщика. Конкретные сценарии дополнительно проверяют отдельные конструкции; полная независимая сверка извлечённой грамматики со стандартом ещё требуется. `./gradlew check` дополнительно запускает встроенную проверку типовых путей через `--check`.

## Как устроены переходы

Импортёр читает правила Annex A из PDF, сохраняет выделенные в нём буквальные терминалы, преобразует альтернативы, необязательные части и повторения в продукции, затем сопоставляет терминалы с реальными `TokenKind` slang. Глобальный граф строится из множеств первых и последних токенов продукций. Пошаговый просмотр использует распознаватель префиксов Earley, поэтому после выбора `module` выводятся `automatic`, `static` и `Identifier`, а после `module Identifier` — `#`, `(`, `;` и `import`. Для каждого следующего токена распознаватель сопоставляет текущие позиции начала правил с их допустимыми первыми токенами. Так после верхнеуровневого `endmodule` двоеточие продолжает тот же модуль, а `module` начинает новый `module_declaration`.

Если выбранный токен из левого списка может начать `source_text`, он открывается в контекстном режиме. Для остальных токенов показывается объединение непосредственных переходов во всей грамматике. В этом режиме каждое ребро обосновано отдельно; составная цепочка может относиться к разным контекстам, поэтому метки начала правил не показываются. Правила и разделы Annex A показаны под графом.

## Состояние инструмента и следующие задачи

Сейчас это просмотрщик **видов токенов**: в GUI можно искать токен, открыть его глобальные продолжения, а исходный текст проходить пошагово с сохранением грамматического контекста и отметками начала именованных правил. Граф включает все 352 вида токенов закреплённой ревизии slang; переходы выводятся из импортированных правил Annex A. Доступны DOT, PNG примера, отчёт об импорте и запускаемый дистрибутив Gradle.

Для более точного ответа на вопрос «какой токен может идти следующим в *этом* коде» нужны следующие шаги:

1. **Выбор произвольного правила в GUI.** Графический интерфейс проходит `source_text`, начиная с `module` или начала файла; CLI позволяет выбрать любое импортированное правило. Если токен из левого списка не может начать `source_text`, GUI показывает глобальные продолжения без контекстной проверки. Для него ещё нужен выбор правила в самом GUI.
2. **Проверка конкретных написаний.** Вершина `Identifier` объединяет любые идентификаторы, а `IntegerBase` — несколько оснований числа. Рёбра не хранят текст лексем и пробелы между ними. Для проверки исходного файла понадобится принимать реальный поток токенов с написаниями и позициями и учитывать ограничения лексера и препроцессора slang.
3. **Сверка всех случаев с закреплённой ревизией slang.** Сейчас тесты покрывают характерные и пограничные пути, но не сравнивают автоматически каждую последовательность с лексером и парсером slang. Нужен воспроизводимый набор примеров или генератор свидетелей для рёбер и тесты на точной ревизии из `SOURCE.txt`.
4. **Доведение импорта до полной лексической части.** `--audit` всё ещё показывает 35 неразрешённых посимвольных обозначений в правилах, недостижимых из `source_text` и `library_text`. Также стоит устранить ручную нормализацию двух повреждённых заголовков PDF и проверить извлечение против другого экземпляра стандарта.
5. **Работа с большим графом.** GUI показывает локальные продолжения и не даёт обзора всех 14 585 рёбер с фильтрацией по разделу стандарта, поиском пути и примерами текста для конкретного перехода. DOT экспорт пригоден для внешних визуализаторов, но интерактивный обзор всего графа ещё не реализован.

## Границы точности

Два заголовка правил в опубликованном PDF набраны как `:: =` и `:=`. Импортёр нормализует только эти разделители до `::=`, сохраняет текст правил и выводит предупреждения. `--audit` перечисляет 35 посимвольных обозначений в лексических и комментарных правилах; из корневой грамматики ни одно из них не достижимо. Значения `binary_value`, `octal_value` и `hex_value` допускают цепочки соседних токенов slang: например, `1x?0` даёт `IntegerLiteral → Identifier → Question → IntegerLiteral`, а шестнадцатеричное `1e2a?f` начинается с `RealLiteral`. Внутри значения переходы повторяются произвольное число раз, согласно Annex A и разбиению лексера. Граф хранит виды токенов, поэтому не проверяет конкретные написания и отсутствие пробелов между частями одного значения; ребро означает существование допустимого написания. Глобальный граф также объединяет контексты разных правил и потому не является доказательством допустимости произвольной цепочки. Проверенный сценарий `module` проходит отдельные проверки.
